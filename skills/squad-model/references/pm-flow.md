# PM 중심 실행 계약

사용자가 정한 운영 구조: **PM이 이 프레임워크를 기반으로 역할을 배분하고 작업을 조율한다.**
coordinator는 별도 상위 직군이 아니라 여기서 PM이 수행하는 조율 책임이다.
제품 판단의 책임과 위임 밖의 승인권은 사용자에게 남는다.
공통 절차 정본은 PRODUCT_WORKFLOW_FILE이며 이 문서는 squad의 배정·인계 계약만 소유한다.

## PM의 입력

- 제품/프로젝트의 목표와 원문 소재, 해당 repo AGENTS 및 현재 task·검증 증거.
- product-workflow skill과 정본, squad-model의 roles/model/handoff/design-tools 참조.
- 실제 사용 가능한 executor/model·도구 연결, 기존 권한·시간/비용 한도와 자원 점유.

## 업무와 배정

| 단계 | PM의 조율 | 참여 역할 / 인계 산출물 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 소재 이해 | 프로젝트·문제·목표·근거와 미지값 식별 | PM: 관찰/해석/가설, 기획: 확인 질문 | 조사 또는 구현 중 착수 범위가 명확 |
| 기준 설계 | 최소 작업으로 분해, 기존 합의 재사용 | 기획: 시나리오/예외, QA: 초기 기준·검증법 | 공통 DoD + task 조건·reviewer·허용 효과 기록 |
| 역할 배정 | 작업별 실제 담당자·모델·도구·한도 선택 | 각 역할: 입력·출력·의존성·공유 자원 확인 | 해당 실행자의 도구/skill 접근 가능; 미합의는 proposed |
| 준비 판단 | 업무 기록에 담당·선행 조건·검토 절차 연결 | 디자인·개발: 준비된 작업 수행 | 선행 검증 완료 + 자원 충돌 없음 |
| 디자인 인계 | 필요한 디자인 작업만 요청·피드백 조율 | 디자인: UIBowl 출처 → Pencil 원본·상태·토큰·증거 | 디자인에 의존하는 개발은 이 인계 검증 후 시작 |
| 구현 | 범위·막힘·남은 한도를 추적 | 개발: 코드 대응표·diff·테스트·브라우저 증거 | 합의 revision/hash에 대한 검증 가능 |
| 검증·수정 | 증거를 기준에 대조, 수정 담당자 재배정 | QA: 기준별 pass/fail/unknown·재현·검증자 | pass면 후속 해제, fail은 범위 내 수정, 한도/권한 문제는 사람 판단 |
| 성과·재개 | delivery와 outcome을 구분하고 다음 작업 선택 | PM: 성과 관찰·학습·새 후보·재개 이유 | 관찰 담당자/트리거와 다음 시작 조건 기록 |

역할 배분은 작업 필요에 따른다. 작은 작업은 PM/기획을 한 executor가 맡을 수 있고,
디자인이 필요 없는 개발은 생략된 디자인 task를 만들지 않는다. QA는 처음부터 기준 설계에
참여한다. 최종 검증의 독립성은 모델명이 아니라 작성·검증 주체와 실제 증거로 표시한다.

## 모델 선택 기록

[handoff.md](handoff.md)의 기존 task 기록에 역할·담당 executor·모델/설정·도구 준비 상태·
배정 이유를 추가한다. 역할은 책임, model은 실행 엔진이다. 업무판과 실행 도구는 별도 선택한다.
PM이 모델을 선택했다고 새 비용·배포 권한이 생기지 않는다. 같은 승인 범위의 배정은
반복 승인을 요청하지 않고 진행하되, 실제 사용할 수 없는 도구를 가정하지 않는다.

현재 시작 후보는 PM=Astra, 기획/디자인=Astra 또는 Sol, 개발=Terra 또는 Sol,
검증=별도 검증 세션이다. 이는 평가 전 배정안이며 고정 정책/실제 agent 설정이 아니다.
Luna는 작은 보조 작업 후보이고 별도 역할 팀을 늘리는 이유가 아니다.

모델·executor 교체 시 task_id와 합의 계약은 유지한다. 입력·산출물·현재 외부 효과·남은
한도·이전 증거를 인계한다. 허용 효과/기준/자원 계약이 바뀌면 revision/hash와 영향받는
증거를 재검토한다. 기존 5개 v1 샘플과 hash 알고리즘은 변경하지 않는다.

이 절차는 PM 지침으로 구성됐다. 자동 모델 선택, 자원 lock, 멀티프로젝트 dispatch는
구현된 기능이 아니다. 선택한 도구의 native 기능을 먼저 사용하며 자체 scheduler는 추가하지 않는다.

## 도구와 무관한 업무 소유권

프레임워크와 기존 권한 안의 배정·착수·검증·수정·후속 진행은 PM에게 위임한다.
제품 방향·합의 기준·권한/비용 범위 변경과 한도 소진은 사용자에게 돌린다.
특정 도구의 ID·명령·세션은 업무 정체성이나 완료 기준을 대신하지 않는다.

- 업무 정체성은 task_id, 기준 버전은 revision/criteria_hash, 순서는 depends_on이다.
- 실행 도구 ID는 별도 연결 기록이다. 입력·권한·기준·결과·남은 일을
  [portable 인계본](handoff.md)에 남긴다.
- 담당자/도구를 바꿔도 남은 한도와 외부 효과를 보존한다. 기준·권한·자원 변경 시에만
  해당 계약 revision/hash와 증거 유효성을 재검토한다.
- 같은 실행 시도에는 하나의 실행 소유자만 둔다. 연락 두절은 종료가 아니며
  다른 도구로 자동 대체 실행하지 않는다.
- 실행자의 완료 보고와 업무의 검증 완료를 구분한다.

현재 Paperclip/Orca를 사용할 때만 [도구 연결 지침](execution-tools.md)을 읽는다.
주기적 운영의 [점검 루프 후보](review-loop.md)는 아직 실행 설정이 아니다.
