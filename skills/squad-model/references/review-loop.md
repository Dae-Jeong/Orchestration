# PM 점검 루프 · 제안

사용자가 말한 루프는 주기적으로 상태를 확인하고 준비된 업무를 이어가는 방식이다.
특정 외부 방법론의 재현을 주장하지 않는다. 현재는 설계 후보이며 schedule/상시 PM을
켜거나 새로운 반복 비용을 승인하지 않는다. 공통 판단은 PM 계약, 도구 연결은
[execution-tools.md](execution-tools.md)가 소유한다.

## 한 번의 루프

깨움 → 상태/변경 확인 → PM 판단 → 권한 안의 실행 또는 대기 → 검증/기록 → 다음 깨움.

1. 업무판·실행 기록에서 새 요청, 질문/결과, 검토 대기, 선행 완료, 장시간 막힘을 확인한다.
   단순 heartbeat나 terminal 존재는 진척·완료 증거가 아니다.
2. 변경이 없고 준비된 일이 없으면 no-op으로 종료한다. 매번 모든 프로젝트를 읽거나
   새로운 일을 만들어내지 않는다. 점검 자체의 모델 호출 비용도 예산에 포함한다.
3. PM은 실제 기준·권한·선행 검증·자원 점유·남은 한도를 대조해 실행/검증/수정/대기/
   사람 판단을 선택한다. 정보 수집이나 시범 성공이 제품 범위 확장을 승인하지 않는다.
4. 같은 업무에 활성 시도가 있으면 새 시도를 시작하지 않는다. 이전 PM 점검과 실행
   소유권을 확인할 수 없으면 중복 시작을 보류한다. 자동 single-flight 강제는 미구현이다.
5. 실행 결과를 검증하고 기준별 증거·외부 효과·남은 일·소진 한도·다음 조건을 기록한다.
   pass는 후속을 해제, fail은 합의된 재시도 안에서 수정, 반복 실패/한도 소진은 사람 판단.
6. 판단할 일이 끝나면 종료/대기한다. 사용자 알림은 결정 필요·검증된 완료·유의미한 막힘
   중심으로 두고, 변화 없는 반복 알림을 기본 동작으로 만들지 않는다.

## 깨우는 방식과 미확정 값

우선 후보는 작업 배정·질문·완료 같은 이벤트로 반응하고 주기 점검을 누락 확인에 보태는
방식이다. 이벤트 전달이 실제 지원·연결됐는지 먼저 검증한다. 주기는 프로젝트의 긴급도와
지연 허용 범위에 따라 선택하며 이 문서에서 임의의 숫자로 확정하지 않는다.

| 실행 전 채울 항목 | 의미 |
| --- | --- |
| 대상 프로젝트·허용 작업 | 어떤 업무를 관찰하고 어떤 효과까지 실행할 수 있는가 |
| 깨움 소유자·주기·운영 시간·만료 | 한 도구만 같은 PM 점검을 깨우며 시범 종료 시점을 둠 |
| 모델·한도 | 1회/누적 시간·호출/비용, 재시도·동시 실행 수; PM 점검과 worker 비용 모두 포함 |
| 중복 방지·재개 근거 | 활성 실행과 외부 효과의 정본, 중단/소유권 이전 확인 방법 |
| 사람 판단·정지 수단 | 결정 담당자, 알림 경로, 사용자가 중단하는 방법과 재개 조건 |

깨우는 도구는 교체 가능하다. 현재 도구의 native schedule/wakeup을 먼저 조사하며,
Orca와 Paperclip 양쪽에 같은 반복 실행을 켜지 않는다. 새 scheduler를 만들지 않는다.
도구나 PM 세션을 바꿔도 retry/cost 한도는 초기화하지 않는다.

## 단계별 도입 후보

1. **수동 1회 점검:** 읽기·판단·기록만 하여 결과/변경 없음/활성 작업 중복을 구분한다.
2. **한정된 주기 점검:** 정해진 시간 동안 관찰·보고만 하고 겹치는 깨움과 중단·재개를 확인한다.
3. **범위 안 자동 진행:** 위 검증 후 준비된 승인 작업만 실행·검증·수정한다.

수용 조건은 no-op에서 실행 없음, 활성 시도 중복 없음, 한도 소진 시 중단,
연락 두절 상태에서 재실행 없음, 기준 변경 시 이전 증거 재검토, 재개 시 외부 효과 보존이다.
이 조건을 실제 runtime에서 검증하기 전에는 자율 루프가 운영 중이라고 표현하지 않는다.
