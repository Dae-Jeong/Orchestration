# 역할 계약

이 저장소의 역할별 인계 계약이다. 공통 행동 규칙은 운영자 global wiki와
`PRODUCT_WORKFLOW_FILE`이 소유한다. 역할 수는 agent/model 수를 뜻하지 않는다.
v1 JSON의 `pm-planning`은 PM과 기획 관점을 함께 담고, `verification`은 QA를 담는다.
기존 enum과 5개 샘플의 ID·revision·hash는 변경하지 않는다.

## PM

- 입력: 원문 근거, 사용자 행동/상황, 리서치·실험 기록, 기존 권한과 제약.
- 책임: 문제·대상 사용자·성과 지표·우선순위·범위/비범위 조율. intake에 관찰,
  해석, 가설을 구분하고 성공·실패·무효 결과와 한계를 연결한다. 대표 성과만 고르면
  선택 기준과 나머지 자료의 범위를 명시한다.
- 판단 권한: 위임 범위에서 분해·순서 제안. 직군만으로 제품 승인권을 갖지 않는다.
- 산출물: 근거가 연결된 문제/성과 질문, 선택 이유, 최소 작업 집합, 측정 계획.
- 시작: 소재와 출처를 읽을 수 있음. 근거 부족이면 조사 작업으로 범위를 한정한다.
- 완료: 대상·문제·범위와 지표 정의/기준선 또는 미지값, 관찰 시점·담당자가 드러나고
  기획·QA가 검증 가능한 질문으로 넘겨받을 수 있음. 미합의 수치/소재는 proposed.
- 다음 인계: 기획·QA에 문제/권한/성과 질문, 디자인·개발에 의존성·제약.
- 실패 귀환: 모순 근거는 intake, 우선순위·허용 효과 변경은 해당 결정권자.

## 기획

- 입력: PM 문제/범위, 원문 근거, 기존 동작과 제약, QA의 초기 검증 질문.
- 책임: 시나리오, 업무 규칙, 상태 전이, 예외·복구, 관찰 가능한 수용 조건 구체화.
- 판단 권한: 합의 범위의 상세화. 새 제품 효과나 정책은 결정권자에게 제안.
- 산출물: 시나리오/상태 표와 기준별 검증법, 의존성·불명확성 목록.
- 시작: 문제와 허용 범위가 특정됨; 상세화 작업 자체도 별도 허용 범위 안에서 진행.
- 완료: 정상·해당 예외 조건이 테스트 가능한 형태이며 reviewer와 미결정 항목 명시.
- 다음 인계: 디자인에 플로우/상태, 개발에 규칙/데이터 경계, QA에 기준 연결표.
- 실패 귀환: 문제·범위 불명확은 PM, 규칙/수용 조건 모순은 계약 조율.

## 디자인

- 입력: 합의 플로우/상태, 사용자 맥락, viewport, 기존 토큰·컴포넌트, 원본 대상.
- 책임: 컨셉 → 출처 있는 레퍼런스 → 시안 → 피드백 → 토큰·컴포넌트 → 개발 인계.
- 판단 권한: 위임된 시각/인터랙션 선택. 기능/권한 변경, 다른 canvas 편집은 별도 범위.
- 산출물: 채택·제외 이유, 리뷰 가능한 원본 버전/노드, 상태·토큰·컴포넌트 매핑,
  viewport별 렌더 증거와 남은 제약. 도구 사용은 [design-tools.md](design-tools.md).
- 시작: 대상 파일/노드와 write 소유권, 기준·viewport가 정해짐; 모르는 것은 proposed.
- 완료: 합의 플로우의 정상·빈값·로딩·실패·복구·권한 등 해당 상태를 다루고,
  토큰/컴포넌트 재사용과 잘림을 검토함. 개발자가 원본과 매핑을 열 수 있음.
- 다음 인계: 개발·QA에 원본/버전/노드·상태·토큰·화면 증거와 미구현 기능.
- 실패 귀환: 시각 문제는 디자인 수정, 행동/정책 모순은 기획, 방향 변경은 결정권자.

## 개발

- 입력: 합의 계약, 기획 규칙, 검증된 디자인 인계, 기존 코드·실행 환경.
- 책임: 재사용 가능한 기존 코드를 확인하고 구현/검증 가능한 변경을 만든다.
- 판단 권한: 허용된 구현 선택. 배포·새 비용·권한 확대는 별도의 기존 승인 근거 확인.
- 산출물: 변경 diff, 토큰→CSS 변수와 컴포넌트→코드 대응표, 실행/검증 증거,
  알려진 한계와 리뷰 가능한 PR 제안.
- 시작: 필요한 선행 검증 완료, 원본 접근, 기준 합의, 공유 파일/DB 충돌 없음.
- 완료: 기준별 코드/테스트 증거, 실제 브라우저 시각·행동 검증과 해당 접근성 기준,
  남은 한계가 제공됨. 디자인 렌더 성공만으로 FE 완료를 선언하지 않는다.
- 다음 인계: QA/reviewer에 commit/diff·재현 절차·기준별 증거; 첫 자동화 도착점은
  검증된 FE 변경 PR 제안. 자동 변환·동기화·배포 완료를 암시하지 않는다.
- 실패 귀환: 구현 결함은 개발, 원본/매핑 누락은 디자인, 규칙 모순은 기획.

## QA / 검증

- 입력: 최초 계약 초안부터 참여하고, 실행 후에는 해당 revision/hash와 산출물을 받음.
- 책임: 초기 기준/검증법 설계, 정상·예외·회귀 위험 확인, 기준별 pass/fail/unknown 판정.
- 판단 권한: 근거에 따른 검증 판정. 제품 범위를 임의로 늘리거나 unknown을 pass로 바꾸지 않음.
- 산출물: 기준별 재현 절차·환경/버전·기대/실제 결과·증거·검증자, 결함의 귀환 대상.
- 시작: 기준 설계는 계약 조율부터; 최종 검증은 접근 가능한 산출물과 고정된 기준 필요.
- 완료: 모든 필수 기준의 판정과 증거가 있고 미통과는 완료 해제를 막음.
  작성자와 검증자가 같으면 self-review로 표시하며 독립 검증으로 주장하지 않는다.
- 다음 인계: pass는 coordinator에 후속 작업 해제 근거, fail은 담당 역할,
  기준 변경/한도 소진/판정 권한 부재는 명명된 사람에게 전달.
- 실패 귀환: 재현 불가는 unknown과 필요한 환경/자료, 기준 모호성은 계약 조율.

## 결정 책임

DACI의 Driver/Approver/Contributors/Informed는 결정별 사람·위임 관계다.
PM·디자인 같은 직군과 별도로 기록하고 역할명만으로 승인권을 추론하지 않는다.
동일인이 여러 관점을 맡을 수 있다. ARPA 명칭의 확장은 이 모델에서 정의하지 않는다.
