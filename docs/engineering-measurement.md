# 변경에 따른 백엔드·프론트엔드 측정 기준

**Task의 목표와 완료 조건을 먼저 정하고, 관련 성능·품질 지표는 필요에 따라 함께 확인한다. 이 목록은 합격 기준표가 아니다.**

확인일: 2026-09-28. 이 문서가 측정 적용 판단·지표 후보·비교 조건·기록·결과 해석을 소유한다. 수동 운영 기준이며 자동 분류·측정·CI gate 구현이 아니다. 일반 실행 절차와 기록 위치는 [운영 모델](task-session-model.md)을 따른다.

## 1. 목표에서 필요한 측정을 선택한다

### 완료 조건과 측정의 관계

| 구분 | 정하는 근거 | 기록과 판단 |
| --- | --- | --- |
| Task 완료 조건 | 사용자 요청·제품 계약·이번 목표 | 충족/미충족/근거 부족. 요구한 동작·결과를 증거로 확인 |
| 목표를 설명하는 측정 | 목표 자체가 성능 개선 등 측정을 필요로 함 | 쿼리 개선이면 전후 시간과 조건으로 개선을 입증. 임의의 100ms 합격선을 추가하지 않음 |
| 함께 확인할 지표 | 변경의 관련 영향·병목·부작용 파악 | 값·변화·해석·한계·추가 확인 필요 여부. 자동 통과/탈락 기준이 아님 |

예: 쿼리 개선은 결과·권한 범위를 유지하면서 실제 개선을 설명해야 한다. 쿼리 시간은 목표의 증거이고, 관련 API 지연·DB 부하는 함께 볼 수 있다. 모든 관측값이 좋아져야 완료되는 것은 아니다. 개선을 확인하지 못했다면 원래 목표가 미입증인 것이지, 공통 KPI 합격선에 탈락한 것이 아니다.

명시적으로 요청된 “p95 300ms 이하”나 이미 적용되는 제품 성능 계약은 해당 Task의 요구로 다룬다. 이 문서나 공개 권고값에서 새 요구를 자동 생성하지 않는다.

### 선택 순서

1. 먼저 Task의 목표와 완료 조건을 정한다. 지표 목록부터 복사하지 않는다.
2. 목표를 입증하는 데 측정이 필요한지 확인한다. 필요하면 지표·측정 경계·비교 조건을 정한다.
3. 추가로 확인할 영향이 있으면 관련 지표만 고른다. 목적이 없으면 측정하지 않는다.
4. 비교 목적이면 변경 전 기준선을 확보하고 작업 후 같은 조건에서 확인한다.
5. 완료 조건의 결과와 추가 관측을 각각 기록한다. 의미 있는 악화는 숨기지 않고 원인·영향·후속 행동을 판단한다.

선택은 **측정함 / 측정하지 않음 / 필요 여부 조사 중**으로 적을 수 있다. 사소한 변경은 이유 한 문장으로 충분하다. 조사 한도 이후 불명확한 추가 지표는 한계로 남긴다. 그것이 원래 목표의 증거라면 목표 미입증도 함께 밝힌다. 매 메시지·매 저장마다 판단을 반복하지 않는다.

기능·권한·정합성·접근성의 관련 동작 확인은 해당 제품 계약과 변경 범위에 따른다. 추가 성능 측정을 하지 않는다는 이유로 생략하지 않는다. 쿼리·캐시 변경의 사용자/tenant 범위, 결제의 중복 효과처럼 실제 영향을 확인하며, 검사 한 건이라는 고정 수로 충분성을 판단하지 않는다.

범위·의존성·실패 관찰이 바뀌면 적용 여부를 다시 판단한다.

## 2. 성과 지표·추가 관측·동작 검증을 구분한다

| 종류 | 역할 | 예시 |
| --- | --- | --- |
| 핵심 성과 지표 | 이번 개선이 성공했는지 평가 | 검색 결과 표시 시간, 성공 처리량 |
| 함께 볼 영향 지표 | 변화와 부작용을 파악; 자동 합격선 아님 | 오류율·메모리·비용 |
| 정확성·안전 조건 | 만족해야 하는 동작 계약 | 중복 결제 방지, 권한 없는 조회 거부, 키보드 조작 |
| 진단 지표 | 원인과 병목 설명 | DB 풀 대기·쿼리 수·긴 JavaScript 작업 |

모든 작업에 성과 KPI가 필요하지는 않다. 결함 수정은 재현 실패 해소와 회귀 확인으로 충분할 수 있다. 지표 개수와 체크 건수는 성과로 쓰지 않는다. 테스트 통과율·커버리지·Lighthouse 종합 점수 하나로 전체 품질을 판정하지 않는다.

실무 기본값으로는 개선 목적이 있을 때 핵심 지표 1~2개와 관련 영향 지표부터 선택한다. 고위험 변경의 필수 검증 개수를 이 권고로 제한하지 않는다.

## 3. 백엔드 지표 선택

| ID·대상 | 적용할 때 | 측정 후보·정의 | 검사·도구 후보 |
| --- | --- | --- | --- |
| BE01 API 지연 | endpoint·쿼리·직렬화·외부 호출 경로 변경, 느림 보고 | route별 p50/p95/p99; 측정 시작/끝과 성공·실패 표본 분리 | OpenTelemetry, 기존 APM, k6 |
| BE02 처리 용량 | 부하 증가·동시성·확장·캐시 전략 변경(캐시 키 변경은 BE06 함께) | 유입/접수/정상 완료 요청 수를 각각 집계; 고정 지연·오류 기준 안의 성공 처리/초 | k6와 서버 지표 |
| BE03 실패·가용성 | 오류 처리·timeout·인증·의존 서비스 변경 | 실패한 유효 요청 / 전체 유효 요청; timeout·예상 거부 분류와 관측 기간 명시 | 요청 metrics·trace·업무 결과 대조 |
| BE04 DB 효율 | SQL·인덱스·ORM·트랜잭션·풀 변경 | 요청당 쿼리 수, 쿼리 시간, 잠금·풀 대기, 처리 데이터량 | pg_stat_statements, 실행 계획, DB/앱 계측 |
| BE05 비동기 처리 | 큐·배치·worker·재시도·전달 경로 변경 | 접수→업무 완료 지연, 가장 오래된 미완료 작업 나이, 적체·재처리·누락·중복 효과 | 업무 ID 원장 대조·큐 지표·통합 시험 |
| BE06 정합성·권한 | 쓰기·동시 갱신·멱등·권한·마이그레이션, 쿼리 WHERE·JOIN·scope 재작성, 캐시 키 변경 | 정의한 시험에서 불변 조건 위반·권한 우회·중복 효과 여부 | 경계·동시성·실패 회귀, 저장 전후 대조 |
| BE07 자원·비용 | 대용량 처리·확장·메모리 문제·유료 호출 변경 | 동일 부하의 CPU·메모리·연결, 정상 완료 1건당 비용 | 기존 infra/APM 지표·비용 원장 |
| BE08 복구·관측 | 복구 로직·배포·timeout·알림 변경 | 정의한 장애의 탐지·기능 복구 시간, 누락 해소, 진단 가능 여부 | 격리된 실패 시험·trace·로그·런북 |

공통 주의:

- HTTP 200이나 프로세스 생존만으로 업무 성공·가용성을 판단하지 않는다. 비동기 접수와 완료를 분리한다.
- 최대 RPS만으로 전체 개선을 주장하지 않는다. 오류·지연 변화도 함께 설명하고 실제 정합성 결함은 수정한다. 추가 수치 변화 자체가 자동 탈락 조건은 아니다.
- p99는 충분한 표본과 분포가 필요하다. 작은 표본의 극단값을 안정적인 운영 수치로 일반화하지 않는다. 집계된 percentile의 단순 평균을 전체 percentile로 쓰지 않는다.
- 4xx 전체를 무조건 실패에서 제외하지 않는다. 예상 검증 거부인지 시스템이 정상 사용자를 거부한 것인지 계약으로 분류한다.
- 복구 시간은 시작점과 사용자 기능 회복의 종료점을 정한다. 실패 주입 구간을 정상 운영 가용성과 혼합하지 않는다.
- 인위적인 DB 재시작·부하 시험은 승인된 격리 환경·자원 한도에서만 수행한다.

## 4. 프론트엔드 지표 선택

웹 프론트엔드 기준이다. 네이티브 앱은 해당 플랫폼의 별도 지표가 필요하다.

| ID·대상 | 적용할 때 | 측정 후보·정의 | 검사·도구 후보 |
| --- | --- | --- | --- |
| FE01 초기 표시 | 첫 화면·이미지·폰트·SSR·번들·데이터 로딩 변경 | LCP, 필요 시 TTFB/FCP로 원인 분석 | web-vitals/RUM, Lighthouse·DevTools |
| FE02 반응성 | 입력·검색·긴 목록·큰 렌더·동기 JS 변경 | 실제 사용자 INP; 로컬에서는 해당 상호작용 지연·긴 작업 | web-vitals, DevTools Performance |
| FE03 시각 안정성 | 이미지 크기·폰트·비동기 삽입·레이아웃 변경 | CLS와 시프트 원인; 대상 viewport에서 레이아웃 확인 | web-vitals, DevTools·화면 관찰 |
| FE04 흐름·오류 | 폼·라우팅·API 연결·낙관적 갱신·인증 변경 | 시나리오 성공, 중복 요청·오래된 응답 오염·미처리 오류, 운영 시 실패 세션 비율 | Playwright·관련 단위/통합 검사·오류 수집 |
| FE05 접근성·표시 | 조작 요소·모달·폼·색상·레이아웃 변경 | 이름·역할·키보드·포커스·대비·확대·반응형 계약 중 관련 항목 | axe와 직접 키보드/화면 검토 |
| FE06 전송·메모리 | 의존성·이미지·폰트·장시간 화면·구독 변경 | route별 압축 전송량, 요청 수, 동일 반복 조작 후 잔류 메모리·미해제 구독 | build 분석·Network·메모리 profiler |
| FE07 사용자 과업 | 핵심 흐름 개편, 사용성 개선 목표 | 과업 완료율·완료 시간·이탈; 관측 대상·기간·실패 정의 명시 | 제품 분석·사용성 시험; 인과 주장에는 적절한 실험 |

공통 주의:

- 화면·인터랙션 변경의 접근성은 관련 기본 동작 검증이다. 별도 KPI 프로젝트가 아니라는 이유로 키보드나 이름·역할 확인을 빼지 않는다.
- axe 통과는 접근성 전체 통과가 아니다. 포커스·키보드와 실제 과업을 직접 확인한다.
- Lighthouse 일반 탐색 실행의 TBT는 INP와 동일한 지표가 아니다. 로컬 결과를 실제 사용자 INP로 기록하지 않는다.
- API 지연이 줄어도 화면의 과업 완료가 빨라졌다는 보장은 없다. 중요한 사용자 흐름은 클릭→화면 결과 확인까지 별도로 정의한다.
- 기능 시험 성공률은 실제 사용자 과업 완료율이 아니다. 전환율 변화는 유입·내용·가격 등의 영향도 받으므로 FE 변경의 단독 성과로 단정하지 않는다.

### Web Vitals 참고값

Google의 좋은 경험 기준은 **LCP ≤ 2.5초, INP ≤ 200ms, CLS ≤ 0.1**이다. 실제 사용자 데이터를 모바일·데스크톱으로 구분하고 p75로 평가한다. 이 공개 권고는 서비스에 채택할 때 관측 범위와 기간을 명시한다. 모든 Task의 즉시 통과값으로 일괄 적용하지 않는다. 표본 부족은 관측 한계로 기록한다. 공개 권고가 Task의 완료 조건으로 자동 승격되지는 않는다.

로컬 성능 시험은 전후 회귀를 확인하는 근거다. Lighthouse 점수나 몇 회의 로컬 실행으로 운영 Web Vitals 통과를 선언하지 않는다. 사용자 표본이 없으면 운영 지표는 미확인으로 두고 로컬 측정 결과를 따로 수용한다. 출처: [Web Vitals](https://web.dev/articles/vitals).

## 5. 변경 유형별로 무엇을 실행할까

아래는 초기 선택 예시다. 실제 영향이 다르면 선택을 바꾼다. 서비스의 지속 계측은 유지하되 관련 없는 Task에서 새 시험을 반복하지 않는다.

| 런타임에 소비되지 않는 문서 오타 | 내용·링크 확인 | 제품 runtime·성능 변화 없음: 부하·Web Vitals 제외 | 수정 완료 시 |

| 첫 화면 이미지·폰트 교체 | FE01·FE03, 전송량·대비/대체텍스트 중 관련 항목 | 관계없는 DB 시험 제외 | 로컬 전후. 관련 운영 관측은 배포 후 후속 확인; 원래 목표가 운영 성과인 경우 그 증거와 구분 |
| 목록 API 쿼리 최적화 | BE01·BE04, 결과/정렬/페이지 회귀; WHERE·JOIN·scope가 바뀌면 변경한 권한/tenant 경계 회귀; 핵심 흐름이면 FE 표시 시간 | 전체 권한 시험을 새로 만들지는 않음 | 같은 조건의 전후 비교 |
| 결제·재고 쓰기 변경 | BE06·관련 BE03/05, FE 중복 제출·실패/결과 불명 처리 | 작은 diff라도 정합성·권한 검증 생략 금지; 최대 처리량은 용량 영향 있을 때 | 격리 통합·실패 시험 후 수용 |
| 큐 재시도 정책 변경 | BE05·BE06·BE08: 중복 효과·누락·적체·복구 | UI 변경 없으면 전체 시각 회귀 제외 | 정상+선택한 실패 경계 |
| JS 라이브러리 추가·긴 목록 변경 | FE02·FE06, FE04/05 관련 회귀 | 모든 route의 전체 측정 대신 실제 영향 route 선택 | build·상호작용 전후 |
| 응답 캐시 도입·캐시 키 변경 | BE01·BE02, BE06: 사용자·권한 차원 분리, 다른 사용자 응답 노출 없음 | 캐시와 무관한 화면 시험 제외 | 캐시 적중·만료 경계 전후 |
| 의존성·lockfile 갱신 | 변경 로그·빌드·관련 기존 테스트; 브라우저 번들 영향은 FE06, 서버 실행 영향은 관련 BE 지표, 개발 도구만 바뀌면 제품 성능 측정 생략 가능 | diff가 작아도 기본 확인 생략 금지; 이유 없는 전체 부하 시험 제외 | 갱신 후 빌드와 관련 흐름 |
| 서비스·노드 증설 | BE02·BE07과 지연·오류 변화와 관련 정합성 확인 | 노드 수만큼 성능 향상을 전제하지 않음 | 같은 조건 전후, 병목 이동 확인 |

흔한 오판: 모든 KPI를 의무 실행, UI 변경이라 접근성 제외, 빠르면 결과 누락도 통과, 작은 diff라 검증 제외, 접수 성공을 업무 완료로 집계, 로컬 1회로 운영 p75 통과, 미수집 데이터를 0 오류로 해석.

증거 재사용과 재실행 조건은 아래 결과 해석을 따른다. 성능 검사 전체를 매 커밋마다 반복하도록 요구하지 않는다.

## 6. 지표와 비교 조건을 정하는 법

**측정 지표를 정하는 것과 통과 목표값을 정하는 것은 다르다.** 목표 자체가 쿼리 성능 개선이라면 전후 측정으로 그 개선을 설명해야 한다. 함께 보는 API 지연·DB 부하에는 자동으로 합격선을 부여하지 않는다. 사용자 요청이나 이미 적용되는 제품 계약에 수치 목표가 있을 때만 그 요구를 기록한다. 공개 권고는 해석의 참고이며 자동 gate가 아니다.

- 비교할 기준선이 없으면 같은 Task에서 변경 전 revision을 대표 조건으로 측정한다. 단순 관측은 항상 전후 비교를 요구하지 않는다.
- 측정 목적·시작/끝·대상·조건·집계 방법을 정한다. 표본 수와 반복에 따른 변동을 기록하되 보편적인 최소 N은 두지 않는다.
- 전후 비교는 부하·데이터·자원·도구 버전·캐시/워밍업·관측 구간을 맞추고 구현 revision 차이를 기록한다. 생성기 포화와 환경 잡음을 확인한다.
- BE는 route·요청 유형·분모·측정 지점, FE는 route·기기·브라우저·네트워크·viewport·상호작용을 명시한다.
- FE lab은 production build나 preview 배포처럼 대표성 있는 환경에서 같은 throttle 조건을 사용한다. 다른 모드를 쓰면 한계를 적는다.
- 오류·timeout·표본 누락을 숨기지 않는다. 자료가 부족하면 판단 불가로 기록한다. 추가 관측 부족과 Task 목표 미입증을 구분한다.
- 같은 조건의 지연 감소율은 `(기준선 - 변경 후) / 기준선`, 처리량 증가율은 `(변경 후 - 기준선) / 기준선`이다. 기준선 0에는 적용하지 않는다. 변동 때문에 차이를 설명할 수 없다면 개선을 단정하지 않는다.
- 운영 성과와 로컬 측정을 구분한다. 추가 운영 관측은 후속으로 남길 수 있으며, 원래 목표의 증거가 아닌 한 Task 완료를 자동으로 막지 않는다.

### 숫자 해석 예시 — 가상의 쿼리 개선

아래 값은 설명용 가정이며 실제 측정 결과나 공통 목표가 아니다.

- Task 목표: 결과와 권한 범위를 유지하면서 목록 쿼리 실행 시간을 줄인다. 특정 ms 목표는 요청되지 않았다.
- 목표 증거: 동일 데이터·요청·측정 경계에서 반복한 쿼리 시간이 380~420ms에서 240~260ms로 변하고 결과·권한 확인이 일치했다고 가정한다. 관측 범위에서 개선을 설명할 수 있다.
- 함께 볼 지표: API 지연과 DB 부하의 변화도 확인한다. API가 빨라지지 않았다면 별도 병목 가능성과 한계를 기록한다. 쿼리 개선 목표에 자동으로 API 합격선을 추가하지 않는다.
- 개선이 관측되지 않았다면: 목표가 미입증이므로 추가 조사한다. 임의로 정한 “300ms 탈락”이 아니다.
- 예외: 원래 요구가 “쿼리 p95 ≤ 200ms”였다면 위 결과만으로 그 요구를 충족했다고 할 수 없다.

## 7. 도구는 필요할 때 연결한다

| 필요 | 도구 후보 | 도입 판단 |
| --- | --- | --- |
| 서버 metrics·trace | OpenTelemetry 또는 기존 APM; JVM이면 Micrometer 고려 | 기존 계측을 먼저 재사용. 동일 지표의 중복 계측을 피함 |
| 지표 저장·조회 | 기존 backend, Prometheus·Grafana | 라이브러리 설치만으로 저장·대시보드까지 생기지 않음 |
| 반복 가능한 HTTP 부하·측정 | k6 | 관련 성능·용량을 볼 때 재사용. threshold/CI 실패 연결은 명시된 요구가 있을 때만 별도로 구성 |
| PostgreSQL 쿼리 진단 | pg_stat_statements·실행 계획 | SQL/DB 병목일 때. 모듈 집계만으로 API p99를 알 수 없음 |
| 웹 사용자 성능 | web-vitals와 수집·집계 endpoint | 운영 표본이 필요할 때; 수집 라이브러리와 저장/집계는 별도 |
| 로컬 웹 성능 | Lighthouse·Chrome DevTools | 로딩·연산·레이아웃의 원인 분석과 전후 비교 |
| UI 동작·접근성 | Playwright·axe·직접 검토 | 변경한 흐름·상태를 우선 검사. 자동 도구만으로 완전성 주장 금지 |

새 SDK·대시보드·부하 인프라를 Task마다 설치하지 않는다. 기존 측정으로 판단할 수 없는 경우에만 계측 작업을 별도로 정의한다. 사용자 ID·원문 URL을 metrics label에 무제한 넣는 등 높은 cardinality와 민감 정보 수집을 피하고 측정 비용도 고려한다.

## 8. Task 기록과 결과 해석

```markdown
Goal: 이번 작업이 달성하려는 결과
Acceptance Criteria: 이번 목표와 기존 계약에서 정한 완료 조건
Scope / 측정 계획:
- 목표 증거에 필요한 측정: 필요할 때만 지표·조건·방법
- 함께 확인할 지표: 선택 이유·방법, 없으면 간단한 이유
- 수치 목표: 명시된 요구가 있을 때만 출처와 함께 기록
Current Result:
- 완료 조건 확인: 결과·증거·남은 일
- 측정 관측: 전후 값·변화·해석·한계·증거
Next Action: 남은 작업 또는 추가 관측의 담당·시점·다음 행동
```

추가 지표를 Acceptance Criteria에 자동으로 넣지 않는다. 모든 칸을 의무 작성하거나 N/A 표를 만들지 않는다. 기록 위치는 [운영 모델](task-session-model.md)을 따른다. 로컬 원시 결과는 핵심 값·조건·revision도 Log에 남겨 참조할 수 있게 한다.

### 결과 해석과 완료

- 추가 측정에 보편적인 합격/불합격을 붙이지 않는다. 개선·악화·비슷함·판단 불가를 근거와 함께 설명한다.
- 추가 운영 관측이나 표본 부족만으로 완료를 막지 않는다. 필요한 관측은 담당·시점·확인 목적을 후속으로 남긴다.
- 목표 자체의 개선 증거가 없거나 명시된 요구가 충족되지 않았다면 완료됐다고 주장하지 않는다. 단순히 측정 실행을 끝낸 것과 개선 달성은 다르다.
- 악화가 관측되면 크기·변동·사용자 영향을 확인한다. 실제 결함·기존 계약 위반은 수정하고, 그 외는 해석과 후속 판단을 기록한다. 사후에 임의 수치를 합격선으로 추가하지 않는다.
- 유효한 기존 증거는 재사용한다. 다른 revision이면 diff·의존성·설정·데이터 변화가 관련 경로에 영향을 주지 않았는지 확인한다.
- 상태와 완료 기록은 [공통 작업 규약 · 로컬 의존성](external-dependencies.md#local-4)을 따른다. 기준 변경은 기존 권한 안에서 이유와 영향을 기록하며, 요청 범위를 바꾸는 결정만 별도로 확인한다.

[가상 Task 적용 예시](engineering-measurement-simulation.md)는 설명용이며 실제 성능 측정 결과가 아니다.

## 9. 출처와 적용 범위

2026-09-28 공식 자료와 기존 지식을 대조했다. 적용 선택표·기록 양식·가상 예시는 이 프로젝트의 구성 기준이며, 외부 표준 인증이나 모든 회사의 KPI를 뜻하지 않는다. JD는 역량 후보를 고르는 참고이며 실제 서비스 목표 수치의 근거로 쓰지 않는다.

- [Google SRE — Implementing SLOs](https://sre.google/workbook/implementing-slos/): 사용자 결과·분모·목표와 측정 구현 구분.
- [Prometheus Instrumentation](https://prometheus.io/docs/practices/instrumentation/): 요청·오류·지연, 비동기 단계, 지표 차원과 계측 고려.
- [OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/), [Micrometer](https://docs.micrometer.io/micrometer/reference/index.html): 계측 역할.
- [k6 Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/): 측정치의 테스트 판정 연결.
- [PostgreSQL pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html): 쿼리 집계 범위. 실제 설치 버전의 지원 필드는 따로 확인.
- [Web Vitals](https://web.dev/articles/vitals), [web-vitals 라이브러리](https://github.com/GoogleChrome/web-vitals): LCP/INP/CLS·p75·field/lab 구분.
- [Lighthouse 점수](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring), [Playwright 접근성](https://playwright.dev/docs/accessibility-testing): 도구 판정의 범위와 한계.
- [로컬 QA 근거 · 로컬 의존성](external-dependencies.md#local-5), [백엔드 신뢰성 · 로컬 의존성](external-dependencies.md#local-6), [컴포넌트 동작 계약 · 로컬 의존성](external-dependencies.md#local-7): 증거 기반 판정, 합성/운영 구분, UI 상태·접근성 선택.
