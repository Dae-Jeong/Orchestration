# 가상 Task 적용 결과

실행일: 2026-09-28. 가상의 링크 보관함 프로젝트에 [수정된 측정 설계](engineering-measurement.md)를 순서대로 적용한 **문서 기반 판단 시뮬레이션**이다. 아래 구현·관측값은 모두 가정 입력이다. 앱·DB·브라우저를 실행하거나 성능을 실제 측정한 기록이 아니며, 자동 판정 엔진도 만들지 않았다.

각 사례에서 ① 목표·완료 조건 → ② 측정 선택 → ③ 가상 관측 입력 → ④ 완료 판단과 추가 관측 분리 순서로 검토했다. 실제 확인한 것은 설계의 판단 일관성이다.

## S1. BE — 목록 쿼리 개선

- 목표·완료 조건: 결과·정렬·페이지·사용자 범위를 유지하면서 목록 쿼리 실행 시간을 줄였음을 확인한다. 특정 ms 목표는 없다.
- 목표 증거의 측정: BE04 쿼리 실행 시간. 같은 데이터 스냅샷·요청 집합·자원·워밍업 조건에서 전후 반복 비교한다.
- 추가 선택: BE01 API 지연. 사용자가 체감할 개선도 있는지 참고한다. UI 변경이 없으므로 화면 전체 성능 시험은 추가하지 않는다.
- 가상 관측: 쿼리 반복값 [400, 410, 390]ms → [250, 245, 255]ms. 중앙값 400→250ms, 37.5% 감소. 관련 결과·권한 검증은 일치. API p95는 620→625ms이며 이 차이의 의미를 판정할 자료는 부족하다.
- 판단: **가정된 범위에서 Task 완료 가능.** 목표인 쿼리 개선과 정확성이 확인됐다. API 지연이 개선되지 않았다는 사실은 추가 관측으로 남기며, 쿼리 목표에 API 합격선을 추가하지 않는다. API 병목은 필요 시 후속 조사한다. 세 번 반복은 이 예시의 가정이며 보편 측정 횟수가 아니다.

## S2. FE — 첫 화면 이미지 교체

- 목표·완료 조건: 요청한 이미지·대체텍스트·반응형 표시가 올바르다. 로딩 속도 개선 자체는 목표가 아니다.
- 측정 선택: 변경의 영향을 보기 위해 FE01 로컬 LCP와 FE06 전송량을 함께 확인한다. 기존에 적용되는 수치 요구는 없다고 가정한다.
- 가상 관측: 화면 동작은 요구대로이며, 동일 lab 조건의 대표값 LCP 2.1→2.4초, 전송량 180→240KB. 실제 사용자 데이터는 없다.
- 판단: **Task 완료 가능, 관측된 악화는 명시.** 수치가 나빠졌다는 이유만으로 자동 탈락시키지 않는다. 이미지 압축·리사이즈 후속 검토를 기록한다. lab 값을 운영 성과로 주장하거나 공개 권고값을 새 합격선으로 쓰지 않는다.

## S3. FE — 버튼 문구 수정

- 목표·완료 조건: 문구·접근 가능한 이름이 요청대로 바뀌고 관련 화면에서 잘리지 않는다.
- 측정 선택: 로딩·연산 경로 변경이 없다고 확인한 가정이므로 추가 성능 측정 없음. 해당 화면과 동작만 확인한다.
- 가상 관측: 문구·표시·동작이 요구대로다.
- 판단: **Task 완료 가능.** KPI가 없다는 이유로 측정 항목을 만들지 않는다.

## S4. FE/BE — 즐겨찾기 저장 기능 추가

- 목표·완료 조건: 본인 항목 저장·중복 처리·실패 안내·새로고침 후 유지가 동작한다.
- 측정 선택: 관련 기능·권한 검증을 수행한다. 추가로 클릭→저장 결과 표시 시간을 관측하고 운영 오류 추이를 추후 볼 수 있다.
- 가상 관측: 기능·권한 결과는 일치. 로컬 클릭→표시 450ms. 운영 오류 데이터는 아직 없다. 수치 요구는 없다.
- 판단: **Task 완료 가능.** 450ms를 임의의 300ms와 비교해 탈락시키지 않는다. 운영 오류 관측은 담당·관측 시점을 후속으로 남기며 미수집을 0 오류로 기록하지 않는다.

## S5. BE — 측정했지만 개선이 불명확

- 목표·완료 조건: S1과 같은 쿼리 개선 목표.
- 가상 관측: 기준선 380~420ms, 변경 후 385~425ms. 환경 변동을 고려해 개선을 설명할 근거가 없다. 결과는 동일하다.
- 판단: **목표 미입증, 조사 계속.** 추가 지표 때문에 막힌 것이 아니라 원래 요청한 개선을 확인하지 못했다. “측정 실행을 마침”을 “개선 완료”로 바꾸지 않는다.

## S6. BE — 빨라졌지만 실제 결함 발견

- 목표·완료 조건: S1과 같은 쿼리 개선 목표 및 사용자 데이터 범위 유지.
- 가상 관측: 쿼리는 400→200ms로 줄었지만 JOIN 변경으로 다른 사용자의 행이 반환된다.
- 판단: **수정 필요.** 속도 관측이 좋다는 이유로 원래 기능·권한 요구 위반을 무시하지 않는다. 단순 수치 악화와 실제 결함을 구분한다.

## S7. 명시적인 수치 요구가 있는 예외

- 목표·완료 조건: 사용자 요청에 “정한 부하 조건에서 API p95 ≤ 300ms”가 명시되어 있다고 가정한다.
- 가상 관측: 비교 가능한 조건의 p95가 500→350ms로 개선됐다.
- 판단: **요구 미충족.** 개선은 기록하되 완료라고 하지 않는다. 300ms는 지표 목록이 만든 합격선이 아니라 이 Task에 원래 주어진 요구다.
