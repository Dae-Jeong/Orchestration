어떤 모델이, 어떤 역할로, 어떻게 일하는가

PM이 우리 프레임워크를 읽고 역할·모델·작업을 배분합니다. 모델은 실행 엔진이고, 역할은 책임·권한·완료 기준입니다.

PM 중심 업무·역할 지침은 구성됐고, 모델명 배정은 아직 제안입니다. 실제 상시 팀은 아직 없습니다. 개발의 직접 진입선은 디자인에 의존하지 않는 준비된 작업만 병렬로 진행한다는 뜻입니다.

하나로 연결한 업무 프로세스

단계PM의 역할참여 역할 → 인계 / 통과 조건
1. 소재·문제프레임워크와 제품 맥락 적용PM·기획: 원문 근거 → 문제·범위·가설. 정보가 부족하면 조사 작업으로 한정.
2. 기준·역할 배분작업 분해와 모델/도구 선택기획·QA: 시나리오·예외·검증법 → 수용 기준·reviewer. 기존 권한·한도를 재사용.
3. 준비·실행의존성·자원 확인, Paperclip 배정디자인·개발: 선행 검증 완료와 자원 비충돌 때 시작. 디자인 의존 개발은 원본 인계를 기다림.
4. 검증·수정증거 확인과 수정 담당 재배정QA: 기준별 pass/fail/unknown. 실패는 범위 안 수정, 기준 변경·한도 소진은 사람 판단.
5. 후속·성과후속 작업 해제와 학습 반영PM: delivery 완료 → outcome 관찰 → 새 후보. 중단·재개 이유와 남은 한도 보존.

작게 시작하는 실행 단위

총괄 1 + 필요한 실행자 + 검증자로 시작합니다. PM·기획을 한 세션이 맡을 수 있고, 디자인이 필요 없는 작업은 개발로 바로 보냅니다. 작성자와 검증자가 같으면 독립 검증으로 포장하지 않습니다.

모델을 바꿔도 task ID·기준·권한·증거와 인계 계약은 유지합니다. 실제 모델 배정은 작업의 난도·도구 접근·한도·검증 결과를 보고 확정합니다.

실제 설정은 어디까지인가

Paperclip의 Design Readiness는 codex_local / paused이며 모델명이 고정되지 않았습니다. 전용 home도 호스트 기본 모델을 명시적으로 복사하지 않아, Astra로 실행된다고 단정할 수 없습니다.

Pencil 연결은 성공, UIBowl은 인증 401입니다. 별도 PM·개발·QA executor나 자동 역할 배정은 아직 구성하지 않았습니다.
