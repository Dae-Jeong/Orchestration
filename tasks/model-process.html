어떤 모델이, 어떤 역할로, 어떻게 일하는가

PM의 업무 계약은 도구와 분리합니다. 아래는 현재 연결안: Paperclip은 업무판, Orca는 제품별 worker의 실행 수단입니다.

ONE DELIVERY TEAM · 논리적 책임 영역

PM · 기획 · 디자인 · 개발 · QA

모델 배정안 · 상시 팀 미기동

모든 역할은 같은 task 기준·권한·증거를 공유합니다. PM이 배정과 진행을 조율하고, 각 역할은 전문 판단과 상세 실행을 맡습니다.

사용자 목표·허용 범위 ⇄ PM | 공통 기준 Product Workflow + Squad 계약 + 프로젝트 규칙 | 현재 도구 Paperclip 업무판 · Orca 실행

실선은 주요 배정·인계, 점선은 초기 검증 협의입니다. 아래 표에 직접 인계·수정 귀환까지 모두 연결했습니다. 선은 자동 실행 순서가 아닙니다. 디자인에 의존하지 않는 개발만 독립 착수할 수 있습니다.

각 역할은 내부에서 어떻게 작업하는가

PM / coordinator

Astra 후보
  1. 원문·제품 맥락 읽기
  2. 문제·우선순위·범위 정리
  3. 기획·QA와 기준 설계
  4. 역할·모델·도구 배정
  5. 질문·검증·후속 조율

받는 것 사용자 목표·권한, 각 역할의 질문·증거 → 내보내는 것 작업 계약, 담당/한도, 다음 시작·대기 조건. 성과 관찰은 새 소재로 연결.

막히면 근거 부족은 조사로, 위임 밖의 방향·기준·권한 변경이나 한도 소진은 사용자에게. 반복 승인은 하지 않음.

기획

Astra / Sol 후보
  1. 문제·기존 동작 확인
  2. 사용자 시나리오
  3. 업무 규칙·상태 전이
  4. 예외·복구 조건
  5. QA와 수용 조건 정리

받는 것 PM의 문제·범위, QA 질문 → 디자인에 플로우·상태 / 개발에 규칙·데이터 경계 / QA에 기준 연결표.

막히면 문제·범위는 PM에게. 디자인/개발에서 발견한 행동 모순은 기획에서 수정하고 기준 영향은 PM과 확인.

디자인

Astra / Sol 후보
  1. 플로우·컨셉 확인
  2. 레퍼런스·선택 이유
  3. 시안·인터랙션 상태
  4. 피드백·수정
  5. 토큰·컴포넌트·렌더

현재 도구 UIBowl 레퍼런스 → Pencil 원본. 개발·QA에 버전/노드·상태·토큰 매핑·viewport 증거·미구현 목록.

막히면 시각 결함은 디자인 수정, 행동·정책 모순은 기획, 방향 변경은 PM. 공유 원본 writer 충돌은 대기. 캔버스 검증과 FE 완료는 별개.

개발

Terra / Sol 후보
  1. 계약·선행 산출물 확인
  2. 기존 코드·토큰 대응
  3. 작은 변경 구현
  4. 테스트·화면/행동 검증
  5. 리뷰 가능한 변경 인계

받는 것 기획 규칙·디자인 원본·허용 환경 → QA에 commit/diff, 실행 환경, 재현 절차, 기준별 증거. 첫 도착점은 검증된 FE 변경 PR 제안.

막히면 구현 결함은 개발 수정, 원본/매핑 누락은 디자인, 규칙 모순은 기획, 새 권한·비용은 PM. 자동 배포 권한을 추론하지 않음.

QA / reviewer

검증자·모델 미정
  1. 초기 기준·검증법 설계
  2. revision/hash 대조
  3. 정상·예외·회귀 재현
  4. 기준별 판정·증거
  5. 귀환·재검증·PM 보고

받는 것 기획 기준, 디자인 상태/화면, 개발 변경/재현 → PM에 pass/fail/unknown, 검증자와 근거. 자가 검증은 독립 검증으로 부르지 않음.

막히면 기준 모호성은 기획·PM, 시각/원본 문제는 디자인, 코드 결함은 개발. 재현 불가는 unknown으로 남기고 필요한 자료를 요청.

역할 간 인계·피드백 계약

역할 간 전문 질문은 직접 주고받을 수 있습니다. 작업 범위·기준·우선순위의 변경과 재배정은 PM이 조율하고 업무 기록에 남깁니다.

연결넘기는 내용수신 측 확인 / 실패 귀환
사용자 ⇄ PM목표·원문·허용 효과 ⇄ 결과·위임 밖 결정기존 합의 재사용. 새 방향·권한·한도 판단만 사용자에게.
PM ⇄ 기획문제·범위·우선순위 ⇄ 시나리오·규칙·미지값관찰 가능한 기준인지 확인. 문제/범위 불명확은 PM에게.
PM ⇄ 디자인디자인 범위·대상·한도 ⇄ 시안·선택 이유·방향 질문기획 기준·원본 소유권·viewport 확인. 제품 방향 변경은 PM에게.
PM ⇄ 개발구현 범위·의존성·환경 ⇄ 변경·진척·기술 제약선행 검증과 쓰기 충돌 확인. 새 효과/권한·한도 문제는 PM에게.
PM ⇄ QA합의 기준·review 권한 ⇄ 판정·재현·잔여 위험증거에 따라 완료/수정/대기 판단. unknown을 완료로 바꾸지 않음.
기획 ⇄ 디자인플로우·정상/예외 상태 ⇄ 사용성·행동 모순빠진 상태를 확인. 행동 규칙 수정은 기획, 기준 변경은 PM과 연결.
기획 ⇄ 개발업무 규칙·데이터 경계 ⇄ 구현 제약·규칙 질문디자인 비의존 작업도 이 계약이 필요. 임의 정책 변경 없이 기획에 귀환.
기획 ⇄ QA시나리오·수용 조건 ⇄ 초기 검증법·예외 질문처음부터 테스트 가능한지 확인. 모호한 기준은 실행 전에 구체화.
디자인 ⇄ 개발원본·버전/노드·토큰·상태 ⇄ 구현 가능성·매핑 질문개발자가 원본을 열고 코드 대응을 확인. 누락은 디자인으로 귀환.
디자인 ⇄ QA상태·viewport·렌더 증거 ⇄ 시각/상태 결함잘림·재사용·해당 예외 상태 확인. 원본 검증이 FE E2E를 대신하지 않음.
개발 ⇄ QAdiff·환경·재현·테스트 ⇄ 실패 사례·회귀 판정기준별 기대/실제 비교. 개발 수정 후 영향 범위를 재검증.
PM → 다음 작업 / 새 소재검증된 완료·남은 일·성과 관찰선행 완료·자원 재확인 후 해제. delivery와 outcome을 분리.

공통 인계 봉투: task_id · revision/hash · 입력/권한 · 완료 기준 · 현재 결과/증거 · 남은 일 · 질문 · 외부 효과 · 남은 한도 · 재개 조건. 앱 ID는 별도 연결 기록입니다.

주기 점검 루프 · 아직 제안

깨움 → 변경 확인 → PM 판단 → 범위 안 실행/대기 → 검증·기록 → 다음 깨움. 새 일이 없으면 실행 없이 종료하고, 활성 시도가 있으면 중복 시작하지 않습니다. 이벤트 반응에 주기적 누락 점검을 보태는 방식이 후보입니다. 대상·주기·비용/시간 한도를 정하기 전에는 반복 실행을 켜지 않습니다.

도구를 교체해도 업무 ID·기준·권한·결과·남은 한도는 유지합니다. portable 인계 양식 · 루프 조건과 단계별 도입안

작게 시작하는 실행 단위

총괄 1 + 필요한 실행자 + 검증자로 시작합니다. PM·기획을 한 세션이 맡을 수 있고, 디자인이 필요 없는 작업은 개발로 바로 보냅니다. 작성자와 검증자가 같으면 독립 검증으로 포장하지 않습니다.

모델을 바꿔도 task ID·기준·권한·증거와 인계 계약은 유지합니다. 실제 모델 배정은 작업의 난도·도구 접근·한도·검증 결과를 보고 확정합니다.

실제 설정은 어디까지인가

Paperclip의 Design Readiness는 codex_local / paused이며 모델명이 고정되지 않았습니다. 전용 home도 호스트 기본 모델을 명시적으로 복사하지 않아, Astra로 실행된다고 단정할 수 없습니다.

Pencil 연결은 성공, UIBowl은 인증 401입니다. 별도 PM·개발·QA executor나 자동 역할 배정은 아직 구성하지 않았습니다.
